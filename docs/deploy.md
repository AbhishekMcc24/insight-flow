# Deploying Insight Flow to Azure Container Apps

Insight Flow deploys with the Aspire CLI. The AppHost (`src/InsightFlow.AppHost`) describes everything. When it
publishes, Aspire turns the local containers into Azure resources and the projects into Container Apps.

> **Every deploy provisions billable Azure resources.** Nothing in this repository deploys automatically: CI only
> builds and tests. Run the commands below deliberately, against a subscription you own.

## What gets created

| AppHost resource | Azure resource | Notes |
|---|---|---|
| `aca` | Container Apps environment + Azure Container Registry + Log Analytics | Hosts all services |
| `postgres` / `insightflow` | Azure Database for PostgreSQL Flexible Server | Password auth; connection string in Key Vault (see "Security") |
| `redis` | Azure Managed Redis | Access-key auth; key in Key Vault |
| `storage` (`blobs`, `extracts`, `files`) | Storage account + blob containers | Managed identity (role assignments are generated) |
| `keyvault` | Key Vault | Created in publish mode only; app secrets (`ISecretStore`) and infra connection strings |
| `migrations` | Container App, 1 replica | Migrates, then idles (`Migrations__KeepAlive=true`; there are no Container Apps Jobs in Aspire 13.6) |
| `queryservice`, `agentservice`, `api` | Container Apps, internal ingress | Replicas 1–5 / 1–3 / 1–5 |
| `worker` | Container App, no ingress | Replicas 1–3; Quartz is clustered |
| `web` | Container App, **external** ingress | 1 replica (see "Scaling the Web app") |

## Prerequisites

1. Azure subscription, with rights to create resource groups and role assignments.
2. [Azure CLI](https://learn.microsoft.com/cli/azure/install-azure-cli), signed in: `az login`.
3. Aspire CLI 13.6+ and Docker (container images are built locally and pushed to the registry).
4. **Microsoft Entra External ID** tenant with two app registrations:
   - **Insight Flow API**: expose the scope `access_as_user`, and define the app roles `Viewer`, `Explorer`,
     `Creator` and `TenantAdmin`. Tokens must carry a `tenant_id` claim with the Insight Flow tenant GUID.
     TODO(dev2): implement that claim with a custom claims provider or a directory extension attribute, plus
     tenant onboarding. See `docs/handoff-dev2.md`.
   - **Insight Flow Web**: a web platform with the redirect URI `https://<web-app-fqdn>/signin-oidc` and the
     front-channel logout URL `https://<web-app-fqdn>/signout-callback-oidc`. Give it a client secret and the
     delegated permission `access_as_user` on the API.

## Deployment parameters

`aspire deploy` prompts for any parameter that has no value. To avoid prompts, set the values as AppHost user
secrets (`Parameters:<name>`) or as environment variables (`Parameters__<name>`).

| Parameter | Secret | Value |
|---|---|---|
| `entra-instance` | no | `https://<tenant-subdomain>.ciamlogin.com/` |
| `entra-tenant-id` | no | Entra External ID tenant (directory) id |
| `entra-api-client-id` | no | Client id of the API app registration |
| `entra-web-client-id` | no | Client id of the Web app registration |
| `entra-web-client-secret` | **yes** | Web app client secret |
| `azure-openai-endpoint` | no | `https://<resource>.openai.azure.com/openai/v1/`, or empty to disable |
| `azure-openai-api-key` | **yes** | Key, or empty when the endpoint is empty |
| `anthropic-api-key` | **yes** | Key, or empty to disable |
| `postgres-username` / `postgres-password` | password is | Generated by Aspire, stored in Key Vault |

Never commit these values. User secrets live outside the repository.

The `Parameters:<name>` keys (with a colon) go into the AppHost user secrets. `Parameters__<name>` (double
underscore) is the environment-variable form of the same setting.

```bash
dotnet user-secrets --project src/InsightFlow.AppHost set "Parameters:entra-tenant-id" "<guid>"
```

## Target subscription

```bash
aspire secret set "Azure:SubscriptionId" "<subscription-guid>"
```

```bash
aspire secret set "Azure:Location" "westeurope"
```

```bash
aspire secret set "Azure:ResourceGroup" "rg-insightflow-dev"
```

For a non-interactive deploy, set the equivalent environment variables instead: `Azure__SubscriptionId`,
`Azure__Location` and `Azure__ResourceGroup`.

## Review, then deploy

First generate the Bicep without touching Azure, and review it:

```bash
aspire publish --project src/InsightFlow.AppHost/InsightFlow.AppHost.csproj --output-path ./artifacts/publish
```

`artifacts/` is git-ignored. Then provision and deploy (**this creates resources and costs money**):

```bash
aspire deploy --project src/InsightFlow.AppHost/InsightFlow.AppHost.csproj
```

Re-running `aspire deploy` updates the resources in place. Schema migrations run at startup of the `migrations`
app. Until it finishes, the other services fail their first database calls and are restarted by the platform.

## After the first deploy

- **No development data is seeded** in Azure. `Seed:DevelopmentData` defaults to false.
- **Authentication is Entra.** The development auth handler refuses to start outside the Development environment.
- **Logs and traces:** the Container Apps environment's Log Analytics workspace. Services export OTLP when
  `OTEL_EXPORTER_OTLP_ENDPOINT` is set.

## Security

- **Postgres and Redis use password/access-key auth.** The Npgsql connection strings used by EF Core and the Quartz
  job store, and the plain StackExchange.Redis client, cannot use Entra tokens yet. The generated connection
  strings are stored in Key Vault and injected as Container Apps secret references.
  TODO(dev2): move both to Entra token auth (`docs/adr/0023-azure-data-auth.md`).
- **Blob storage and Key Vault use managed identities**, with generated role assignments.
- Only `web` has external ingress. The APIs are reachable inside the environment only.

## Scaling the Web app

Blazor Server keeps each user's circuit in memory, and the auth cookie is protected with ASP.NET Core Data
Protection. To run the Web app on more than one replica, first:

1. Persist the Data Protection key ring, e.g. in a Blob container protected with a Key Vault key.
2. Enable sticky sessions on the `web` container app (`Ingress.StickySessions.Affinity = Sticky` via
   `PublishAsAzureContainerApp`).
3. Raise `WithReplicas(min: 1, max: 1)` for `web` in `AppHost.cs`.
